# Композиция и компонентный подход в Unity

Переносимая выжимка пользовательского руководства Unity Way.
Примеры исходных игр и зависимости от их классов исключены.
Это рекомендации для Unity, а не описание уже существующей архитектуры нового проекта.

## Основные принципы

Один компонент отвечает за одну возможность: движение, здоровье, обнаружение цели, cooldown, звук или визуальную реакцию.
Объект-координатор хранит явные зависимости и связывает возможности; предметную логику держи в компонентах или обычных C#-классах.
Игрок и AI могут вызывать один и тот же API действия, отличаясь источником команд.
Общие интерфейсы нужны там, где есть несколько реализаций и реальная граница ответственности.

## SOLID на практике

| Принцип | Практическое правило |
|---|---|
| SRP | Ввод, применение действия, проверка условий и эффекты не становятся одним большим контроллером. |
| OCP | Добавляй условия и реакции через существующие точки расширения вместо цепочки проверок конкретных классов. |
| LSP | Реализация интерфейса сохраняет его контракт и ожидаемые побочные эффекты. |
| ISP | Предпочитай узкие роли вроде `IDamageable` большому интерфейсу персонажа. |
| DIP | Предметная логика зависит от контракта; конкретные ссылки назначаются в точке сборки. |

## Декомпозиция фичи

1. Опиши результат одним предложением и зафиксируй сценарии и ограничения.
2. Выдели аспекты: ввод, поиск цели, физика, условия, cooldown, состояние, визуальные эффекты, звук.
3. Проверь существующие компоненты прежде, чем создавать новые.
4. Определи владельца состояния и публичный API каждого аспекта.
5. Определи события и время жизни связей.
6. Собери зависимости в координаторе и проверь, что действие работает с разными источниками команд.

Не превращай каждый метод в отдельный компонент: деление оправдано самостоятельной ответственностью и жизненным циклом.

## Зависимости и события

Inspector связывает конкретные Unity-компоненты; доменная логика может получать зависимости через конструктор или явную инициализацию.
Компонент действия не должен знать все возможные причины запрета действия.
Если уже есть механизм предикатов вроде `AddCondition(Func<bool>)`, координатор добавляет условия извне.
Условия, захватывающие временный объект, должны удаляться вместе с ним.

В `Awake` задавай постоянные зависимости и условия.
В `OnEnable` подключай реакции событий, в `OnDisable` отключай их.
При другом lifetime выбирай симметричную пару и учитывай повторное включение объекта и pooling.
Не создавай циклическую цепочку событий без явного владельца перехода состояния.

## Композиция или наследование

Композиция подходит, когда поведение нужно комбинировать независимо.
Наследование подходит для настоящего отношения `is-a` или Template Method с общим устойчивым алгоритмом.
Повтор одного метода и желание «сэкономить несколько строк» не являются достаточной причиной вводить базовый `MonoBehaviour`.
Число наследников и процент общего кода сами по себе не доказывают правильность наследования.

## Практический чек-лист

- У каждого компонента одна ясная причина изменения.
- Ввод и AI отделены от выполнения действия.
- Настраиваемые поля приватные и сериализованные, ссылки назначены явно.
- Поиск компонентов не выполняется каждый кадр.
- Подписки и временные условия освобождаются.
- Между физикой 2D и 3D нет случайного смешения API.
- Эффекты и звук реагируют на событие, а не определяют исход действия.
- Проверены повторное включение, отключение, уничтожение и повторное использование объекта.
- Комментарии описывают неочевидную причину; очевидное выражено именами.
