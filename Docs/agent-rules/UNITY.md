# Unity

Применяется только к Unity-проектам.
Версию бери из `ProjectSettings/ProjectVersion.txt`, пакеты — из `Packages/manifest.json` и `packages-lock.json`.
Не устанавливай пакет и не меняй render pipeline только потому, что они встречались в исходном проекте.

## Доступ к Editor

- Проверяй подключение к Editor именно текущего проекта.
  При нескольких экземплярах явно укажи корень проекта через поддерживаемый параметр инструмента.
- Если Unity CLI установлен и поддержан проектом, предпочитай его для работы внутри Editor; MCP для Unity — запасной путь при недоступной команде или соединении.
  Если CLI отсутствует, используй доступный MCP без обязательной установки CLI.
- Для CLI сначала проверь доступные команды (`unity --help`, затем поддерживаемые status/query команды).
  В проектах с соответствующим API применимы `unity cmd editor_status`, `unity cmd --query <term> --detail full`, `unity recompile` и чтение ошибок Console.
  Не считай этот набор универсальным для любой версии инструмента.
- Иерархию, компоненты, сериализованные значения и реальную геометрию UI проверяй через живой Editor.
  Используй Undo и сохраняй изменённые сцены/префабы.
- Ручная правка `.unity` / `.prefab` / `.asset` YAML — крайний путь.
  Если Editor нужен для задачи и CLI/MCP недоступны, сообщи конкретное ограничение и один раз уточни: запустить Editor или продолжить файловые правки с обозначенными ограничениями.
  Продолжай независимую работу с кодом, если она уже разрешена.
- Не меняй существующие GUID и не теряй `.meta` при переносе Unity-ассетов.
  Не удаляй `Library` и другие кэши ради неподтверждённой гипотезы.

## Компоненты

- Используй композицию: одна ответственность на компонент, контроллер/ввод отдельно от предметной логики.
- Зависимости компонентов задавай через `[SerializeField] private`, где это подходит; доступ снаружи — через осмысленный API/read-only свойства.
- Не вызывай `GetComponent` в `Update` / `FixedUpdate`; кешируй ссылки или назначай их в Inspector.
  Для динамического поиска предпочитай `TryGetComponent`, по возможности через интерфейс.
- Связывай независимые реакции событиями; подписывайся в `OnEnable`, отписывайся в `OnDisable` либо используй симметричную пару по фактическому lifetime.
- Условия действия задавай извне через предикаты/существующий механизм условий.
  `AndCondition` — пример подхода, а не обязательная зависимость нового проекта.
- Компоненты — `*Component`, контроллеры — `*Controller`, события — `On*`, если существующий проект не задаёт другую последовательную схему.
- Группируй serialized-поля в Inspector через `[Header]`.
  Odin-атрибуты используй только при установленном Odin и соответствующем соглашении проекта.
- Порядок членов: события, константы, serialized-настройки, serialized-зависимости, приватные поля, свойства, Unity callbacks, публичные методы, приватные методы.
  Порядок callbacks: `Awake`, `OnEnable`, `Start`, `Update`, `FixedUpdate`, `OnDisable`, `OnDestroy`.
- До реализации опиши фичу одним предложением, выдели аспекты, компоненты, интерфейсы и события.
  Наследование допустимо для реального `is-a` или общего алгоритма с вариативными шагами.

Подробности и схема декомпозиции: [руководство по композиции](../Guides/UNITY_COMPOSITION_GUIDE.md).

## Проверки

Проверь компиляцию, Console и соответствующий сценарий EditMode/PlayMode по доступным возможностям проекта.
Если нужны визуальные или layout-изменения, проверь результат в Game view/реальном префабе.
Проверка исходников не равна успешной проверке в Editor.

## Multiplayer Play Mode — только если установлен

Главный Editor является обычной целью изменения ассетов и запуска проверки.
Виртуальные игроки `Library/VP/<id>` используются намеренно для многопользовательского сценария; они могут разделять `Assets` с главным Editor.
Проверь `projectPath`, чтобы не отправить компиляцию или правку префаба не тому экземпляру.
Останови Play Mode перед правками скриптов; не запускай конкурирующие операции изменения одних ассетов.
Не коммить `Library/VP`; конкретные правила тестовых аккаунтов задаются в `PROJECT.md`.
