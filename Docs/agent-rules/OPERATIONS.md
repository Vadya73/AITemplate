# Исполняемые проверки агента

Все команды запускаются из корня проекта с Python 3.10+ и установленным PyYAML.
Секреты и машинные пути в конфигурацию не добавляются; необходимые значения берутся из окружения по правилам конкретного проекта.

## Команды

| Команда `python Scripts/agent.py ...` | Назначение | Запись в проект |
|---|---|---|
| `doctor` / `doctor --json` | Окружение, схема конфигурации, готовность адаптации | Нет |
| `doctor --strict` | То же, предупреждения считаются ошибкой | Нет |
| `verify fast` | Индексы, ссылки, skills, быстрые команды продукта | Только возможные побочные эффекты явно настроенных команд продукта |
| `verify full` | Fast и полные команды продукта; тесты инфраструктуры при `tooling_tests: true` | То же |
| `sync` | Пересобрать документацию | Только изменившиеся источники frontmatter и результаты |
| `status` | Актуальность по отпечаткам и текущая Git-диагностика в stdout | Нет |
| `attest Docs/example.md --reviewed` | Записать факт завершённой сверки текста с кодом и пересобрать индекс | Да |

Коды `verify`: 0 — выбранный набор прошёл, 1 — ошибка, 2 — продуктовые проверки выбранного профиля отсутствуют.
У исходного шаблона нет приложения; его профиль проверяет именно инфраструктуру.
В исходном шаблоне full всегда включает тесты инструментов; в игровом проекте они включаются отдельно при изменении инфраструктуры.
В установленном проекте отсутствие команд продукта не превращается в успешную проверку продукта.
`status` — диагностика, а не оценка качества текста; отсутствие Git не мешает статической проверке отпечатков.

## Конфигурация команд

В `.agent/project.json` массивы `verification.fast` и `verification.full` содержат объекты с `name`, `argv`, необязательными `cwd` и `timeout_seconds`.
Пример безопасной проверки в проекте с соответствующим Python-тестом:

```json
{
  "name": "Focused tests",
  "argv": ["{python}", "-B", "-m", "unittest", "tests.test_feature"],
  "cwd": ".",
  "timeout_seconds": 60
}
```

Это пример формата, не готовая команда любого проекта.
Список аргументов запускается без shell; `{python}` заменяется текущим интерпретатором, `{root}` — корнем проекта.
Рабочий каталог должен находиться внутри проекта.
Для `.cmd`/`.bat` на Windows нужен явный подходящий исполнитель; предпочтительнее непосредственно исполняемый CLI или Python/Node-скрипт.
Не добавляй в проверку миграции, релиз, публикацию и операции с БД.
Настроенные команды считаются доверенным кодом проекта, поэтому просматривай их перед первым запуском в неизвестном репозитории.

## Завершённость задачи

До реализации существенной задачи зафиксируй ожидаемый результат и способ проверки.
После изменения запусти соответствующий профиль или более узкую реальную проверку, если общий профиль избыточен.
В отчёте различай выполненные команды, их результаты, недоступные проверки и незавершённые требования.
Проверка документации не подтверждает работу приложения, а наличие тестов не означает их запуск.

## Hook

В `hook` поддерживаются `mode: check|off`, `enforce: false|true`, `cache: true|false`, `timeout_seconds`.
По умолчанию hook проверяет только документацию и не запускает команды продукта.
При ошибке он выводит сообщение; при `enforce: true` возвращает JSON-блокировку Stop.
Повторное событие с `stop_hook_active: true` получает сообщение без новой блокировки, чтобы не зациклить агента.
Ошибки конфигурации и запуска показываются пользователю; они не маскируются под успех.

Кеш хранит только успешный результат и ключ по путям, размерам и времени изменения входов, включая индексируемый код и результаты.
Он лежит вне репозитория в системном временном каталоге и не содержит текстов исходников.
При восстановлении файлов с сохранением размера и mtime отключи кеш или выполни `verify fast`; ручная проверка и CI не используют этот кеш.
Автоматического `sync` нет: эта запись выполняется явно внутри задачи с разрешёнными изменениями.

## Границы доступа

Правило Markdown само по себе не является техническим запретом.
Для обязательного ограничения доступа к БД/секретам используй права окружения, отсутствие ненужных credentials и соответствующие ограничения установленного агента.
Шаблон не переносит универсальные разрешения и не объявляет регулярное выражение над shell-командой надёжной защитой.

## Выпуск и обновление шаблона

`template.json` фиксирует версию, явный перечень payload, политику владения и SHA-256 каждого файла.
`managed` — общие инструменты и правила; `seed` — начальные проектные настройки, знания и производные индексы.
Установщик сравнивает входящую версию с baseline receipt и текущим файлом, проверяет весь план до записи и не удаляет устаревшие файлы автоматически.
Для изменения и upstream, и локальной версии требуется ручное объединение.
`--accept-merged <путь>` означает явное подтверждение уже выполненного объединения и сохраняет его локальное содержимое.
После обновления выполни `sync` и проверки проекта; миграции формата проектных настроек при необходимости выполняются отдельно.
