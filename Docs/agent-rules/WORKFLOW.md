# Подробные правила разработки и документации

Загружай нужные секции при работе с архитектурой, документацией или нетривиальным изменением.
Краткие постоянно действующие правила находятся в корневом `AGENTS.md`.
Проектные факты и исключения находятся в `Docs/agent-rules/PROJECT.md` от корня проекта.
Незаполненный пункт означает «неизвестно», а не разрешение придумать значение.
Явные инструкции пользователя в текущей задаче важнее настроек шаблона.

## Начало работы

1. При неизвестных проектных правилах открой `Docs/agent-rules/PROJECT.md`; учитывай применимые вложенные `AGENTS.md`.
2. Начни знакомство с системой с `Docs/INDEX.md`; для терминов используй `Docs/_brain/glossary.md`.
3. Подключай тематические правила по задаче: [C#](CSHARP.md), [Unity](UNITY.md), [композиция Unity](../Guides/UNITY_COMPOSITION_GUIDE.md).
   Правила Unity действуют только для Unity-проектов; C# — только для C#.
4. Проверь состояние рабочего дерева и существующие изменения пользователя перед правками.
5. Для новой кодовой базы сначала установи реальные точки входа, зависимости и команды проверки по файлам проекта.
   Не выдавай рекомендации из шаблона за уже установленный стек.

## Общение и выполнение

- Объяснения и документация — на русском; код, идентификаторы, комментарии и сообщения коммитов — на английском, если проект не требует иного.
- Отвечай кратко, конкретно, дружелюбно, без вводной воды; сначала результат, затем необходимые пояснения.
- Считай пользователя опытным разработчиком.
  Объясняй причину проблемы простым языком и обосновывай решения фактами.
- Перед правками обдумай ограничения и подход; для существенной задачи кратко сообщи план действий.
  Не требуется публиковать внутренние рассуждения или фиксированное количество абзацев.
- Доводи согласованную задачу до проверяемого результата.
  Не останавливайся на описании возможного решения, если можешь выполнить работу.
- Различай факт, гипотезу и непроверенное предположение.
  Рассматривай несколько причин ошибки до выбора исправления.
- Если неизвестное требование, архитектурный выбор, состояние релиза или контракт влияет на результат, уточни его до зависимых изменений.
  Объединяй вопросы и предлагай рекомендуемый вариант; используй доступный инструмент вопросов или обычный текст.
  Рутинные обратимые детали реализации решай самостоятельно в рамках уже согласованной задачи.
- Предлагай полезные улучшения и нетривиальные решения, когда они помогают задаче; не расширяй объём правок без необходимости.
- Не добавляй нравоучений и отвлечённых предупреждений.
  Обсуждай существенный и неочевидный риск, если он влияет на действие пользователя.

## Изменения и данные

- Делай минимальное полное исправление, сохраняй существующее поведение вне согласованной задачи.
  Изучи затронутые пути исполнения, вызовы и контракты до правок.
- Не откатывай чужие изменения и не выполняй разрушительные операции Git без явного запроса.
  Коммит, публикация и отправка в remote выполняются по запросу пользователя.
- Никогда не подключайся к реальной или локальной БД и не читай/изменяй её данные напрямую.
  Не запускай SQL-клиенты, запросы, применение или откат миграций.
  Пиши код, параметризованный SQL и файлы миграций; пользователь выполняет операции с БД сам.
- Не правь сгенерированные файлы вручную.
  Найди источник и генератор; специфические ограничения и команды возьми из `PROJECT.md`.
- Не переноси в репозиторий секреты, токены, локальные разрешения агента, машинные абсолютные пути и историю чужого проекта.
- Строй новое простым, читаемым, модульным кодом.
  Композиция и явные зависимости предпочтительнее глубокого наследования.
  Следуй SOLID/GRASP без создания абстракций ради абстракций.
- Держи файлы небольшими и сфокусированными, ориентир — до 200 строк.
  Не дроби связный код только ради числа строк.
- Комментарий нужен для неочевидной причины, ограничения, обхода ошибки SDK или важного порядка действий.
  Не пересказывай код, не дублируй имена и документацию; предпочитай понятное имя или отдельный метод.

## Проверка результата

- После значимого изменения запускай подходящую проверку поведения, сборку или имеющиеся тесты.
  Масштаб проверки должен соответствовать риску изменения.
- Не заявляй об успешной компиляции, тестировании в Editor или работе hook без фактической проверки.
  Если среда недоступна, явно назови, что не проверено.
- Новые тесты должны проверять контракт и ошибки поведения, а не повторять реализацию.
- В отчёте укажи результат, важные изменения, выполненные проверки и существенные ограничения.
- Коммиты должны быть небольшими и законченными; формат номера задачи определяется проектом.
  В PR укажи проблему, итоговое поведение и проверку; для UI приложи доступное визуальное подтверждение, для codegen — список обновлённых артефактов.

## Документация и Second Brain

- Документация является частью изменения: обновляй описание изменённого контракта в той же задаче/коммите.
  Код — источник истины о текущем поведении; обнаруженное расхождение исправляй в документе.
- Читай нужные секции по диапазонам в `Docs/INDEX.md`, не весь массив документации.
  Для поиска кода сначала используй `Docs/_brain/index/symbols.tsv`, если язык поддержан и индекс содержит нужные данные; затем адресный `rg`.
- Поперечные вопросы ищи в `Docs/_brain/registries/`, типовые процедуры — в `Docs/_brain/playbooks/`.
  `Coverage.md` связывает документы с путями кода; `Stale.md` показывает ограничения актуальности.
- Новую сложную механику, интеграцию или неочевидный контракт документируй по [плейбуку](../_brain/playbooks/document-a-mechanic.md).
  Добавь документ в `Docs/_brain/brain.yaml`, свяжи с соседями относительными Markdown-ссылками.
- Ставь `verified: YYYY-MM-DD` только после фактической сверки документа с кодом.
  `python Scripts/agent.py attest Docs/<файл>.md --reviewed` сохраняет дату и отпечатки перечисленных файлов; это явное подтверждение автора, а не автоматическая оценка качества.
  Черновики помечай `status: partial` или `missing` и оставляй `verified` пустым.
- Подтверждённую ловушку запиши самостоятельной строкой с `⚠️` в соответствующем документе.
  Новое соответствие русского термина и кода добавь в глоссарий.
- После примерно 2500 слов выноси справочные таблицы, карты файлов и сценарии в подстраницы с `parent: <id>` в `brain.yaml`.
  Инварианты, поток данных и ловушки оставляй в основном документе.
- Завершённый отчёт задачи относится к Git/PR, а не к постоянному описанию механики.
  В `Docs/Memory/HANDOFF.md` сохраняй только незавершённую работу и проверяемый контекст следующей сессии.
- После изменения документов, конфигурации индекса или индексируемого кода выполни `python Docs/_brain/build.py`.
  Стандартный hook только проверяет; синхронизацию выполняй явно в задаче с разрешёнными изменениями документации.
- `Docs/INDEX.md`, `_brain/DATA.md`, `_brain/index/*`, `_brain/registries/*` генерируются.
  При конфликте сначала разреши исходные документы и `brain.yaml`, затем пересобери результаты.
- В рукописном Markdown используй отдельную исходную строку на предложение/самостоятельное утверждение.
  Не переноси прозу по фиксированной ширине, не переформатируй чужие абзацы; строка таблицы остаётся одной строкой.

## Windows и инструменты

- Поиск начинай с `rg` / `rg --files`, при отсутствии используй доступный аналог.
  Группируй независимые чтения и проверки.
- Предпочитай MCP или нативный инструмент shell-команде при равных возможностях.
  Минимизируй видимые окна терминала; фоновые процессы запускай без окна или со скрытым окном.
  Не пропускай необходимую проверку ради этого предпочтения.
- Для путей PowerShell используй `-LiteralPath`, где это уместно.
  Перед рекурсивным удалением/перемещением проверь абсолютный путь и его принадлежность нужному каталогу.
- Не передавай удаление из PowerShell в `cmd /c` и не собирай операции с файлами строковой интерполяцией.
  Не используй `$HOME` и другие системные переменные для временных значений задачи.
